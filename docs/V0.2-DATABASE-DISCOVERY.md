## Architecture decision

Keep ASP.NET Core MVC/Razor and the existing four layers. Domain now contains City,
Category and DiscoveryEntry persistence entities without EF dependencies.
DiscoveryItem remains the immutable read projection consumed by the application
and view model. Infrastructure owns EF mapping, migrations, the Npgsql repository
and design-time migration factory. No Nuxt, generic repository framework,
background worker, authentication framework or API has been introduced.

Web registers a scoped DbContext and repository. Application services pass a
validated DiscoveryFilter and cancellation token. The in-memory demo repository
exists only in the foundation test assembly; there is no runtime fallback.
Database outages produce the existing generic production error response.

## Schema and query behavior

- Cities and categories have unique normalized slugs.
- Every discovery entry has required city/category foreign keys, required bounded
  content fields, a slug unique within its city and an explicit published flag.
- Database constraints reject malformed slugs and blank titles. Parent deletes
  are restricted while content references them.
- Migration seeds one city, five categories and six synthetic entries. Generated
  identities start at 1000 to avoid collisions with reserved fixture IDs.
- Queries require a valid city slug, include published content only, filter in
  PostgreSQL, project only display fields, use AsNoTracking and await ToArrayAsync.
- Category matching is normalized; text search uses parameterized ILIKE with
  escaped %, underscore and backslash, preserving literal substring behavior.
- Results are ordered by ID and capped at 100. The UI asks users to refine search
  at the cap. Pagination, relevance ranking and full-text indexes are deferred.
- Composite city/publication/category indexes support scoped filtering. The small
  synthetic dataset does not justify performance or production-scale claims.

The Almere deployment fixes its city scope server-side; city/citySlug query
parameters cannot change it. Tests create temporary Utrecht content inside a
rolled-back transaction and prove separation. This is application-level public
content scoping, not PostgreSQL row-level security or completed multi-city
authorization. The runtime role can read all public catalog rows. Do not put
private tenant data in this schema without a separate authorization design.

## Local database security

compose.yaml runs a digest-pinned official PostgreSQL 18 image, bound only to
127.0.0.1:55432. It uses separate persistent data and TLS volumes. Bootstrap
generates random local passwords in ignored .env and a 90-day development TLS
certificate inside the container. Only its public certificate is copied out.
Clients require SSL Mode=VerifyFull, checking trust and hostname. PostgreSQL
rejects plaintext TCP and uses SCRAM password authentication over TLS.

happy_app has CONNECT, schema USAGE and SELECT on migration-created tables.
It cannot create tables or write content. The migration identity is a local
development database administrator; it is not supplied to the web process.
Production must use separately provisioned, least-privilege migration credentials,
managed secrets/certificates and approved deployment controls.

Unix socket trust is limited to the development container, whose administrators
already control the database files. This Compose setup is not a production
deployment template. No production database or external service is provisioned.

Database exception details and parameter logging are forbidden by connection
validation; routine SQL command logs are suppressed. Existing HTTPS, CSP, HSTS,
antiforgery and rate limiting remain intact. Search terms may still appear in
browser history or operational logs; no personal information should be entered.

## Reproducible setup

Prerequisites: pinned .NET 10 SDK, Docker with Linux containers, PowerShell
(Windows PowerShell locally or pwsh in CI), and a trusted HTTPS dev certificate.
From the repository root:

```powershell
dotnet restore HappyAlmere.slnx
./scripts/Initialize-LocalDatabase.ps1
dotnet build HappyAlmere.slnx -c Release --no-restore
./scripts/Test-Local.ps1
./scripts/Start-Local.ps1
```

Open https://localhost:7143. Initialize may be rerun: existing credentials/volumes
are retained and EF applies only pending migrations. It never drops databases.
Do not remove .env independently of the persistent database: that would lose the
matching credentials. Keep local credential files private, and never publish them.
The scripts are for this disposable synthetic-data database only.

VS Code F5 reads .env.runtime, which bootstrap generates with only the read-only
connection. The Test and Run HTTPS tasks use the same scripts. Interactive
debugger breakpoint testing has not been performed.

Stop the app before rebuilding on Windows. Stop PostgreSQL without deleting data:

```powershell
docker compose stop postgres
```

The development certificate expires after 90 days. Renew it through an explicit
local certificate maintenance operation and refresh artifacts/postgres.crt.
Do not bypass trust checking to work around expiration.

## Migrations

The pinned local dotnet-ef tool and Infrastructure design-time factory use
HAPPYCITY_MIGRATION_CONNECTION, separate from ConnectionStrings__HappyCity.
Application startup never creates, seeds or migrates the database.

```powershell
. ./scripts/Load-LocalEnvironment.ps1
dotnet ef migrations add DescriptiveChange --project HappyAlmere_V0.1_MVC/src/HappyCity.Infrastructure
dotnet ef migrations script --idempotent --project HappyAlmere_V0.1_MVC/src/HappyCity.Infrastructure
```

Review generated changes before applying them. Down removes the new schema and
data and is destructive; it was not executed. The initial migration is for the
synthetic prototype, not for importing customer data.

## Verification

Local checks on 19 November 2026:

- Release and Debug builds: passed, zero warnings/errors.
- 63 tests passed, none failed or skipped. Includes the original 31 foundation
  tests, explicit city validation and TLS policy tests, and real PostgreSQL tests.
- PostgreSQL tests cover migration repeatability/model drift, Dutch text and
  literal search, SQL-like hostile input, no tracking, city/draft exclusion,
  bounded results, constraints, read-only grants, actual TLS, rejected untrusted
  certificates, rejected plaintext TCP, cancellation, MVC integration and outage
  behavior. Test writes roll back; only synthetic seed rows persist.
- Chromium HTTPS smoke tests passed at 320/375/768/1024/1440 px, all eight distinct
  navigation destinations, search, empty state, category retention and skip focus.
  No horizontal overflow or browser errors were observed.
- NuGet direct/transitive audit: no known vulnerabilities reported.

Run all tests with Test-Local.ps1; real database tests deliberately fail if their
configuration or database is missing. For a quick database-free middleware/unit
check, use dotnet test --filter "Category!=Postgres". Such a subset is not the
full release verification.

CI provisions its own synthetic TLS PostgreSQL using the same bootstrap and runs
all tests. It uses pinned official Actions, read-only GitHub permissions, masked
ephemeral credentials, a fixed runner family and a time limit.

## Git review gate and remaining limits

main now requires a pull request, an up-to-date branch, the verify status check
from GitHub Actions and resolved review conversations. Rules apply to admins;
force pushes and branch deletion are blocked. No independent approval count is
required because no separate reviewer has been established. Human review and
merge authorization remain part of the agreed workflow.

Work stays on develop and is proposed through a PR; no automatic merge or
production deployment is performed. Production backups/restore, monitoring,
identity, private-data authorization, data retention, cross-city administration,
real content approval and performance/load verification remain future work.
